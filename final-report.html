The Case of the Quiet Heroes!

What Release 4.2 really did, and the fix

On 12 August a release meant to help made four of our sixteen responders go silent. The average said everything was fine. This is how we found out, what we'd build, and how the next investigation avoids the same trap.

1

What happened, plainly

Rook Dispatch: incident comes in → rank responders → offer the job to the top one → accept, decline or time out → on to the next
12 Aug

The release

Release 4.2 shipped three things that matter: distance counts more in the ranking (45% → 60%), the offer timer was cut from 90 to 60 seconds, and a few small fixes.
=

The rule

In the code, running out of time is scored exactly like saying no. Both take off 0.12 points. Only an accepted job adds points back (+0.08).
0

The trap

Nothing ever lifts a score by waiting. A hero who is rarely asked never gets the chance to earn it back. An open question from 2019 sits above that code.
73%

The disguise

The headline success rate dipped to 54% and climbed back to 73%. It looks like recovery. Underneath, four heroes were left behind.
HOW SURE ARE WE?

Most likely cause (medium to medium-high confidence): the 60-second timer pushed more missed offers, missed offers were scored as refusals, and the score has no way to recover on its own. Five separate reviews, each blind to the others at first, landed on the same answer, and a direct read of the code agrees.

Not yet confirmed: the server logs (were these misses recorded as timeouts?), Wen's intent, and where each hero lives. Our notes also say the "just a quiet August" idea is weakened but not ruled out, because we have no August from past years to compare with.

ISSUE 04

X-Ray Vision: reading the code, no coding needed

THE FINDING

One line takes points off. One line puts them back.

In history.py, the function that docks points for a refusal also docks them for running out of time: "Same either way." The only thing in the whole file that adds points back is an accepted job. No decay, no reset, and a 2019 note from Wen asks if scores should ease back over time. It was never answered. So the trap is older than 4.2; the shorter timer pushed more people into it.

The fix, in my prototype

Show who has gone quiet. Give them a way back. Be honest about what we can't promise.
KIP'S SCREEN, TODAY vs WITH THE FIX

Today, Kip (a handler) sees two cards and nothing that explains why one hero is idle and the other is slammed. With the fix, each card says why, and there is one button. Try the button:

Meteor Mite

1 offer this week (usually 11)

Calls aren't reaching them. A few missed calls pushed them down the list.

Uses the override handlers already have (added in 4.0).

The Gale

21 offers this week (usually 13)

Doing extra work while others are quiet.

Helping the quiet hero should also lighten this load.
Numbers are from the callout file and the brief. The button here is an illustration of the screen, not a working feature.
THE THREE PARTS
  1. Say it first. A short, plain message to affected heroes: a change in August cut offers for some people, it isn't their fault, an update is coming by a date we can keep.
  2. Show a "My offers" screen. Offers got, taken, and missed over four weeks, with a clear line that the account is fine.
  3. Give a comeback offer. The first offer after a long quiet gets extra time, and running out of time doesn't count against them.
THE RULE UNDERNEATH
  • Running out of time is not the same as saying no. It should cost less.
  • A hero's place in line should recover after a quiet time. Today it stays stuck.
  • A one-time lift for the four heroes who are left out right now.

In the Fix Options model, putting the timer back alone leaves about 8 in 10 left-out heroes still left out; adding the lift brings most back in about 3 weeks. Example numbers, not a forecast.

How the sidekick stops a repeat

What went wrong in 4.2, and which skill step would have caught it

4.2 WENT WRONG

  • A change shipped with no success measure you could point to
  • Two things changed at once
  • An average hid four people
  • A cause was assumed ("it's August") before any data
➜

THE SIDEKICKS

review-checklist reads a brief before work starts and flags: no owner, no way to tell it worked, scope that grows, or a fix pitched before the problem.

product-investigation runs the method that found this: a 95% confidence gate before any analysis, rows shown behind every headline number, and "who does each source not cover?"
➜

NEXT TIME

A brief for a ranking change must name an owner and a measure (for example, offers per responder, not only the average) before it ships. A drop is investigated with the split first, and nobody names a cause the data can't yet support.
THE GATE · product-investigation

Before any analysis, the skill must be at least 95% sure of four things. The lowest score wins; if any is under 95 it asks up to four questions, each with a best guess so "yes" is enough.

  • The ask: exact deliverable and what's out of scope
  • Who I am: role, boss, what I already know
  • The goal: the decision, by when, what "good" looks like
  • Its role: what it does alone vs. checks with me first

Nothing gets built until the gate passes, there's a direction to show, and I choose among prototype, one-pager, PRD and slide deck.

THE CHECK · review-checklist

Pointed at a folder, it reports like this. It never rewrites the brief. This is the course's example report for the four sample briefs, which my skill is built to reproduce:

routing-override-audit-log.txt
  owner named ........... yes (Marcus's team)
  success measure ....... NO — flagged
  scope stays bounded ... yes
  problem before fix .... yes
  -> 1 flag: no success measure. Says what gets
     logged, never how anyone would know it works.

Scheduled to run every Monday around 8:11 AM (first run 12 Oct) over 06-sidekicks/briefs/. The app has to be open.

THE SHORT VERSION

What happened: a faster timer plus a scoring rule with no way back quietly shut four of sixteen heroes out, while the average looked like it was recovering.

The fix: make the quiet visible, give them a comeback path, and stop treating a missed offer like a refusal.

Staying safe: use the skills so the next brief names an owner and a measure, and the next investigation shows the rows before it names a cause.

What isn't proven yet

Read this before you repeat any of the above to Helen
TO BE HONEST
  • The cause is strongly indicated, not confirmed. We still need the server logs, Wen's intent for the timer, and (for the four) where they are in relation to most incidents. If they are also far away, moving them up the list may not bring calls back, because distance is 60% of the ranking.
  • We have not spoken to a real responder. The practice interviews were simulated and shape the screens only.
  • "Just a quiet August" is weakened (a sharp 20+ point drop in the exact release week, concentrated on four people) but cannot be ruled out without last year's data.
  • This repo can't verify "4.2 only changed settings". It has just one commit touching the routing code, already after 4.2, so no before/after comparison exists here.
  • Skills are tested lightly. I wrote the tests myself, the fresh briefs were easy (the plain model also got every one), and neither skill is installed in .claude/skills/ yet, so the trigger wording is untested.
  • Asks still unsent: Ravi (what the ping columns measure, daily data), Wen (intent, location), Nadia and Helen.
